# LP-0005: Private Token Balance Attestation

**Status**: Not entered. Prize text captured; design notes only.
**Prize URL**: https://ns.com/LP-0005.md
**Fit**: Adjacent infrastructure with direct reuse potential for Operator Uplift's Pro-tier gating.

## Prize summary (from Logos Press)

Many access-control mechanisms (governance participation thresholds, protocol fee tiers, allowlist eligibility, token-gated chat rooms) require a user to prove they hold at least N tokens of a given type. On a transparent chain this is trivial: anyone can inspect the balance. On Logos, balances are private by default, which breaks the naive approach but **enables a much better one**: a user can prove they meet a threshold without revealing the actual balance.

This prize is for a reusable LEZ primitive that takes a private account + a threshold + a token type, and produces a zero-knowledge attestation that the holder meets the threshold.

## Why this is hard

- The attestation must be **rebuildable across nonces**. Account state changes (deposits, withdrawals) shift the balance; the proof has to be either re-issuable or scoped to a specific block height.
- The attestation must be **transferable**: a verifier checks the proof without going through the prover's account.
- Replay protection: an attestation issued at height 100 must not be passed off as fresh at height 1000 if the balance has since dropped.

## What we would build

1. A Risc0 circuit that proves `balance(account, token) >= threshold` given the prover's private balance witness.
2. A LEZ program that issues + verifies these attestations, with a `nonce` field bound to the issuing block to prevent replay.
3. A reference TypeScript client that builds the witness from a private-account RPC + submits the attestation to any consumer contract.
4. A test suite covering threshold edge cases, replay attempts, and balance-decreased-after-attestation cases.

## Why we (Operator Uplift) care

This primitive maps directly to **Pro-tier gating**. Today, our paywall checks a Supabase row (`subscriptions.status = 'active'`). On Logos, the same gate could be expressed as "holds >= 1 PRO_TOKEN" with the user proving membership without us ever seeing their wallet balance. That is the cleanest version of "verifiable subscription" we could ship.

The Pro-tier gating use case also means we have a real downstream consumer for this primitive, which strengthens any submission.

## What we would NOT do

- Reinvent the token program. We'd use the existing LEZ token program (which LP-0013 separately improves).
- Build a UI; deliverable is the primitive + reference client.
- Solve cross-chain attestation. Single-chain LEZ only.

## Operator inputs needed before ship

- Funded LEZ testnet wallet.
- Sample token mint on LEZ testnet for the test suite (could be created as part of the entry).
- Decision on whether to scope to "any token type" or "PRO_TOKEN specifically" for the demo. Scoping narrower ships faster.

## Estimated effort

2-3 weeks. Less than LP-0002 because the threshold predicate is simpler than the multisig state machine.
