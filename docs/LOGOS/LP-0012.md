# LP-0012: Event/Log mechanism for LEZ

**Status**: Not entered. Prize text captured; design notes only.
**Prize URL**: https://ns.com/LP-0012.md
**Fit**: Infrastructure piece. Needed indirectly by LP-0008.

## Prize summary (from Logos Press)

A structured event system that lets LEZ programs emit events describing what happened during execution. Events must be:
- **Human-interpretable** for debugging and wallet UX.
- **Machine-readable** for indexers, explorers, and apps.
- **Retrievable** by clients after execution.
- **Still emitted** even when a transaction fails.

The prize calls out that other ecosystems (EVM logs, Solana program logs) have established patterns to learn from but not copy verbatim.

## Why this is hard on LEZ specifically

- LEZ programs run in Risc0, which means events have to flow out of the zkVM into the host context without breaking proof generation.
- The "still emitted on failure" requirement means events can't ride on top of the same commit semantics as normal state changes.
- Private programs need to emit events without leaking private witness data; the event schema has to support a `public`/`private` distinction per field.

## What we would build

1. An event type system in the LEZ program SDK (Rust) with field-level public/private tags.
2. A Risc0 host-side capture layer that pulls events out of the zkVM transcript even when the program panics or aborts.
3. An on-chain event index program that lets clients query events by program, by topic, and by block range.
4. A reference indexer (TypeScript) that subscribes to the event index and powers a wallet UX demo.
5. Documentation comparing the LEZ approach to EVM `LOG0`-`LOG4` and Solana program logs, with honest tradeoffs.

## What we would NOT do

- Build a general-purpose explorer UI; the indexer + demo is enough to prove the primitive works.
- Solve cross-program event composition (one program subscribing to another's events). That is a follow-up prize.

## Operator inputs needed before ship

- Funded LEZ testnet wallet.
- Access to current LEZ runtime + Risc0 toolchain version compatibility matrix.

## Estimated effort

3-4 weeks. The "still emitted on failure" requirement is the riskiest piece because it changes the proof-generation semantics.
